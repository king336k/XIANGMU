# EngramProject 部署说明

## 交付文件

一条打包命令生成三个独立压缩包：

| 产物                                           | 内容                                                                   | 何时更新               |
| ---------------------------------------------- | ---------------------------------------------------------------------- | ---------------------- |
| `EngramProject_code_<版本>.tar.gz`             | 后端业务、前端构建、协作服务、诊断逻辑、数据库迁移、配置模板和启停入口 | 日常功能更新           |
| `EngramProject_images_<版本>.tar.gz`           | 固定运行镜像、依赖版本清单、BGE权重、镜像加载工具                      | 首次安装或运行依赖变化 |
| `optional/frp/EngramProject_frp_<版本>.tar.gz` | frp程序、配置模板、DAQ适配和说明                                       | 按需安装或升级通道     |

三类产物都有版本信息、逐文件校验清单和归档SHA256。合并基础知识用于工作区首次初始化，之后以独立数据库为准，升级不覆盖用户知识。代码包不包含运行数据库、密码、模型权重、用户附件或日志。镜像版本一致时，业务更新只传代码包。frp默认不启动，同机和普通内网部署不依赖它。

附带的开发说明和历史测试记录供参考，部署包不包含完整开发工具或历史验收附件；其中的源码工具、旧报告链接需在完整源码及相应证据目录中查看。目标服务器安装与升级以本说明和包内脚本为准。

## 打包机

打包机需要当前代码、构建工具、Docker及匹配目标架构的已准备镜像。首次准备运行环境和模型属于镜像发布步骤；日常打包不自动下载权重或构建运行镜像。

```bash
# 从仓库根目录一键编译并生成三个独立产物
./package-offline.sh --artifact all --build --output /绝对路径/交付目录

# 已有前端和协作构建产物时，仅生成业务部署包
./package-offline.sh --artifact code --output /绝对路径/交付目录

# 检查镜像和模型是否齐全，不导出大镜像文件
./package-offline.sh --artifact images --verify-only --output /绝对路径/检查目录
```

模型和frp二进制位于其他目录时，分别使用`--model-dir`、`--frp-bin-dir`。打包不会覆盖同名旧归档，不清理已有交付目录。当前无Git提交时，版本记录真实的文件树摘要及不可用的HEAD，不伪造提交号。

## 目标服务器

目标需要Docker、Compose v2、Python 3.10或更新版本、tar、sha256sum，以及足够的磁盘和内存；业务运行无需安装Node、pnpm、编译工具或模型SDK。镜像包的架构必须匹配目标。公网入口另需配置可访问地址、网关及TLS证书。

先校验归档旁的`.sha256`文件，再解压镜像包。运行其中的`load_images.sh`，用`--deploy-root /绝对部署目录`将已验BGE模型放到该部署的共享目录。已有匹配镜像和模型时可跳过镜像包加载，禁止用删除其他项目镜像来释放空间。

解压代码包，先检查，再明确安装：

```bash
python3 deploy/release/install.py --package /路径/EngramProject_code_版本.tar.gz --deploy-root /srv/engramproject
python3 deploy/release/install.py --apply --package /路径/EngramProject_code_版本.tar.gz --deploy-root /srv/engramproject
```

首次安装会检查 `--port` 指定的首选端口；若被占用，依次尝试其后最多99个端口，不停止占用者。检查及安装结果的 `access_url` 和 `port` 给出最终入口，安装后保存在 `shared/.env` 及 `shared/last-install.json`。检查模式不写配置，实际安装时重新核对端口；已有部署的升级沿用保存的入口，不自动改端口。

例如将平台部署给内网其他电脑访问：

```bash
python3 deploy/release/install.py --check --package /路径/EngramProject_code_版本.tar.gz --deploy-root /mnt/sdg/engramproject --project-name engramproject --bind 0.0.0.0 --host 10.10.10.4 --port 8886
python3 deploy/release/install.py --apply --package /路径/EngramProject_code_版本.tar.gz --deploy-root /mnt/sdg/engramproject --project-name engramproject --bind 0.0.0.0 --host 10.10.10.4 --port 8886
```

`--host` 只接受IP或域名，不含协议、端口和路径。部署器据此设置网页地址、CORS和Cookie域；不会修改服务器网卡IP。端口探测与Docker绑定之间存在短暂竞争窗口，若其他程序恰好抢占端口，安装保留失败记录和已有服务，须核对后重试。

默认入口仅绑定本机。需要其他电脑访问时，在部署配置中设置实际入口地址、绑定地址和访问源，配置TLS或上层网关后进行验证。不要把模型、数据库、对象存储及内部通道端口直接开放公网。

## 目录与日常操作

```text
部署目录/
├── start.sh / stop.sh        # 部署根的一键启停入口
├── current -> releases/当前版本/
├── previous -> releases/前一版本/
├── releases/                 # 独立业务版本，保留旧版供核对
└── shared/
    ├── .env                 # 本机生成的私密配置，升级保留
    ├── deployment.json      # 部署身份、启用模块和运行参数
    ├── models/              # 低频更新的已验BGE权重
    ├── logs/                # 运维导出的服务日志和升级前归档
    └── backups/             # 升级前数据库备份
```

数据库、对象存储、附件及队列使用固定部署身份的数据卷，不随业务版本目录变化。安装器不得接管另一个部署的容器或卷；普通启停不删除卷。

```bash
cd /srv/engramproject
./start.sh
./stop.sh
python3 current/deploy/release/launcher.py status --deploy-root /srv/engramproject
python3 current/deploy/release/launcher.py logs --deploy-root /srv/engramproject
```

部署根的启停脚本始终选择current，升级后仍使用相同入口，不覆盖自行创建的同名脚本。启动只使用本地已校验镜像，不编译、不拉取。问答模型由管理员在页面配置；内置语义检索由平台接通，无需在每个项目重复填写。OCR保留人工核对要求，不以识别完成表示内容准确。

## 升级、日志与失败恢复

日常升级沿用同一部署根目录，只安装新代码包。运行依赖改变时，先加载新镜像包。升级前应导出旧容器日志并备份数据库，验证迁移和服务健康后再切换`current`；新版本失败时保留旧版本、备份和失败阶段记录。

API、普通后台任务、定时任务、诊断worker、协作、网页访问、向量、OCR及基础服务的标准输出与错误由各容器记录，默认按20MiB×5份轮转。保留量有限，长期归档应导出到`shared/logs/`或接入外部日志存储。业务操作和诊断报告的历史另保存在业务数据库，不等于容器日志。

日志不保存密码、令牌、Cookie和认证头；请求及异常仍保留用于定位的路径、状态和耗时。网页访问日志与浏览器控制台错误不同，当前不把用户浏览器中的全部控制台内容自动上传服务器。

检查服务可使用`launcher.py status`，日志可使用`launcher.py logs`导出。若存在未完成部署事务，先核对记录、迁移与备份，不直接删除事务标记或强行切版本。数据库迁移不能仅通过切回旧代码目录撤销；涉及不可逆迁移须制定恢复方案。

## frp按需启用

frp源码位于`deploy/network/frp-bridge/`；交付产物位于统一交付目录的`optional/frp/`，独立解压和配置。公网端及指定的联网采集网关各运行对应角色，数据平台无需安装frp；普通内网直接连接。首次配置和验证完成后，采集员继续按原DAQ流程操作。

frp包只提供检查及显式启动入口，不自动安装系统服务或修改网卡、路由、防火墙和DNS。密钥与证书由部署人员在目标环境配置，不写进交付包。详细配置见frp包内README。

## 验收范围

标准安装会自动初始化本说明末尾的合并基础知识版，工作区项目可直接检索。旧157历史包的显式导入工具仅供归档恢复；后续升级保留知识数据库，不覆盖用户增改或恢复已下线内容。

首次部署应验证登录、项目权限、附件上传下载、后台队列、诊断及知识检索；升级应验证数据、附件、配置和日志保留以及运行镜像ID未无故变化。当前开发过程的测试报告与目标环境验收分别记录，不能由打包成功推断部署成功。

## 五种业务角色

| 角色     | 职责                                                                             |
| -------- | -------------------------------------------------------------------------------- |
| 管理员   | 全部岗位业务及平台设置，可自行提交、处理、审核、确认和关闭，操作记录使用本人身份 |
| 项目经理 | 项目成员岗位、需求与任务、缺陷分派、方案审核、测试最终确认、项目发布和报表       |
| 技术员   | 分析分派问题、提交技术方案和修复结果、发起验证、补充经验知识                     |
| 测试员   | 维护用例、套件、测试计划和资源，安排执行、提交结果，发起回归和生成测试报告       |
| 数采员   | 采集任务、上报问题、补充本人材料、查看获授权的处理结果                           |

技术员和测试员是预置岗位。所有登录账号由当前平台创建，管理员按项目分配岗位；不再提供外部账号登录、账号互认、项目任务同步或外部数据回归。首次空库部署自动创建初始管理员，重复部署保留已有账号及已修改密码，不重置。

合并DAQ继续沿用原有采集员登录流程。其反馈服务直接向项目管理平台签名提交问题和附件，只携带当前DAQ账号编号、用户名快照，不导入密码、不创建采集员登录账号或项目成员。所有已接入采集电脑共用“设置 → DAQ 项目授权”清单，只能向明确分配的项目反馈，无需给DAQ分配工作区。授权变更使用版本校验，搜索与分页保留未保存勾选。

部署时在采集端服务器配置 `PROJECT_FEEDBACK_URL`、`PROJECT_FEEDBACK_KEY_ID`、`PROJECT_FEEDBACK_SECRET`、`PROJECT_FEEDBACK_AUDIENCE`；在平台私有部署环境配置 `QUALITY_DAQ_REPORT_KEYS_JSON`，每项包含 `secret`、`audience`、`source_instance`。密钥只在服务端配置，不进入前端。该密钥仅授权专用反馈接口，不能创建浏览器会话或操作普通项目API。初始项目授权清单为空，由管理员在页面勾选后生效。禁用来源密钥立即停止该来源反馈。

测试员不自动获得项目最终验收、发布或全平台设置权限；普通岗位保留原审批边界，管理员无需第二人即可审核本人事项。飞书相关后续完善已延期，不作为本次交付前置。

## 常用入口

统一从“右上角头像 → 设置 → 成员与权限”管理人员。选择项目后，在同一人员表添加成员、修改岗位或兼任；管理员可切换“全部人员”，在同一个编辑入口管理管理员身份。访问范围和业务岗位分别保存，并明确显示保存结果。DAQ项目授权、协作服务、平台连接和模型配置位于同一设置导航。管理员拥有全部岗位能力，以本人账号操作和留痕。

项目内“需求”处理正式需求、审批及变更，“任务”及项目保存的任务视图只展示研发任务；跨项目的“工作总览”保留需求和任务综合查询。编号、关联和历史记录保持。测试区保留用例、用例集、计划、执行记录、测试资源和测试结果；发布验收位于“版本迭代 → 发布验收”。文档知识区使用“项目文档、知识库、知识问答、知识管理”等名称。

旧测试配置和模型连接地址会跳转到新入口，并保留项目、查询及页内定位。菜单归位不重建账号、项目或业务记录；已存链接、编号与后端接口继续兼容。

项目侧栏中“我的项目 → 项目 → 三个点 → 项目菜单设置”可勾选六个主要菜单。取消“测试”等项只隐藏该项目侧栏和顶栏的导航入口，不删除记录、不改变权限；项目成员共用设置，至少保留一个入口。历史项目默认全部显示。

## 默认 AI 能力与升级保留

标准部署默认提供 PydanticAI 自动诊断引擎和 `bge-small-zh-v1.5` 内置知识检索模型。PydanticAI 使用工作区配置的对话模型；新部署未填写对话模型密钥时保留规则诊断，不显示为模型诊断已完成。BGE 权重随运行环境包离线安装，标准部署无需再次配置外部向量接口。模型页面分别显示诊断引擎、检索服务状态和检索模型名称。

工作区内所有项目共用该工作区模型配置，不同工作区分别保存。升级保留数据库中的工作区模型配置、加密密钥和 `shared/.env`，不会用默认值覆盖；旧版全局配置作为未单独设置工作区的兼容默认。自定义模型域名通过私有部署配置 `KNOWLEDGE_LLM_ALLOWED_HOSTS` 保留，代码包不含模型账号密钥。

导入知识时，普通文本直接解析；PNG、扫描PDF以及包含图片的DOCX在通过原件检查后自动排队OCR，不需要选择是否启用。失败时显示原因并允许重试，重复预检不重复排队。识别结果先预览和核对，再导入知识草稿。

## 默认基础知识（platform-base-20261111-v1）

首次安装在“平台基础知识”项目中自动初始化17条已发布基础知识：6条平台使用和通用排查内容，与原11条历史参考资料合并为同一版，历史适用范围和原始版本保留。当前工作区现有项目及后续新建项目默认可检索。不同工作区不跨区共享。

管理员可在基础知识项目中新增、修改、下线和发布知识。升级只对尚未初始化的工作区建立初版，不覆盖已有修改、不恢复已下线或删除条目、不把新部署包中的种子重新灌入。初始化标记与知识数据库一起持久化。基础知识发布新版本后，仍启用的工作区共享跟随新版本，明确撤销的共享不自动恢复。

旧legacy-157知识包保留为历史导入和校验材料；标准安装使用随后端代码交付的合并基础版，不要求再次人工导入该历史包。

## 仅项目平台的公网 FRP 开关

已授权的固定入口为 `180.153.172.19:18886`，只转发到本机持久配置中的 `HTTP_PORT`（例如 `8886`）。开关属于安装器与持久部署，不修改或重启原 `frpc`，原 SSH/VNC 等代理保持独立。

```bash
# 当前已安装部署：只关项目公网代理，不停止内网应用
python3 /mnt/sdg/engramproject/current/deploy/release/install.py \
  --deploy-root /mnt/sdg/engramproject --apply --closefrp
# 原配置已选择 Docker 后端时重新打开
python3 /mnt/sdg/engramproject/current/deploy/release/install.py \
  --deploy-root /mnt/sdg/engramproject --apply --openfrp
# Docker 创建受阻时显式选择独立 systemd 用户单元；须先停旧的本项目受管 Docker 代理
python3 /mnt/sdg/engramproject/current/deploy/release/install.py \
  --deploy-root /mnt/sdg/engramproject --apply --openfrp \
  --frp-backend systemd-user --frp-source-config /opt/frpc/frpc.toml \
  --frp-python /home/engram/miniconda3/bin/python3
# 随正常代码包安装/升级显式关闭公网
python3 deploy/release/install.py --package /absolute/EngramProject_code_VERSION.tar.gz \
  --deploy-root /mnt/sdg/engramproject --apply --closefrp
```

`launcher.py --deploy-root ROOT --openfrp/--closefrp` 和更新后的 `ROOT/start.sh --closefrp` 同样只操作该公网代理；带 FRP 开关时不隐含启动/停止应用。两个开关互斥。不传开关：新安装默认关闭，升级保持既有状态；已开启的 Docker 代理会随本机应用端口更新。systemd 后端端口需要变化时先显式关闭再打开，避免运行中单元与状态不一致。

原始 TOML 只读，持久 `shared/frp-state.json` 仅有服务器、端口、镜像、来源路径、受管容器/单元等公开状态，不写入 token。Docker 后端只继承认证、传输、服务器公共配置，在 tmpfs 中生成一条 TCP 代理配置；systemd 后端在 `/dev/shm` 中生成 `0700/0600` 临时配置。均不继承旧代理与旧管理端口，专属状态接口只绑定 `127.0.0.1` 的空闲端口。开成功须确认 FRP 状态中的本代理 `running` 与远端 `18886`，并不以进程创建成功代替注册成功；仍须单独真实访问公网完成验收。

容器名/单元名由部署根摘要确定，操作前检查 ownership 标签或单元描述与命令。关闭只停止该部署的受管代理；不删业务资料、内网 Compose 或旧 `frpc`。出现 Docker/系统命令超时或所有权不符时拒绝，并保留现状供检查，不承诺公网已关闭。显式切换后端前必须先关闭已记录后端。

诊断超时：部署目录 `shared/.env` 中可设置 `DIAGNOSTIC_TIMEOUT_SECONDS=300`，默认5分钟，有效范围60～600秒。
调整后重建 API 和诊断 worker 容器使设置生效。诊断在后台执行，关闭页面不取消任务；超时仍保留规则结果。
诊断使用独立 `diagnostics` 队列；默认同时分析2条，额外任务等待，不占用上报请求。可用 `DIAGNOSTIC_CONCURRENCY` 调整并发。
排队最长默认6小时，可通过 `DIAGNOSTIC_QUEUE_WAIT_SECONDS` 调整为900～86400秒，避免延长诊断后批量任务15分钟即过期。
