# EngramProject 部署说明

## 交付文件

一条打包命令生成三个独立压缩包：

| 产物 | 内容 | 何时更新 |
| --- | --- | --- |
| `EngramProject_code_<版本>.tar.gz` | 后端业务、前端构建、协作服务、诊断逻辑、数据库迁移、配置模板和启停入口 | 日常功能更新 |
| `EngramProject_images_<版本>.tar.gz` | 固定运行镜像、依赖版本清单、BGE权重、镜像加载工具 | 首次安装或运行依赖变化 |
| `optional/frp/EngramProject_frp_<版本>.tar.gz` | frp程序、配置模板、DAQ适配和说明 | 按需安装或升级通道 |

三类产物都有版本信息、逐文件校验清单和归档SHA256。157初始知识仅用于首次初始化；导入成功后以独立数据库为准，后续程序升级不再导入、同步或覆盖初始知识。代码包不包含运行数据库、密码、模型权重、用户附件或日志。镜像版本一致时，业务更新只传代码包。frp默认不启动，同机和普通内网部署不依赖它。

附带的开发说明和历史测试记录供参考，部署包不包含完整开发工具或历史验收附件；其中的源码工具、旧报告链接需在完整源码及相应证据目录中查看。目标服务器安装与升级以本说明和包内脚本为准。

## 打包机

打包机需要当前代码、构建工具、Docker及匹配目标架构的已准备镜像。首次准备运行环境和模型属于镜像发布步骤；日常打包不自动下载权重或构建运行镜像。

```bash
# 从仓库根目录一键编译并生成三个独立产物
./package-offline.sh --artifact all --build --output /绝对路径/交付目录

# 已有前端和协作构建产物时，仅生成业务部署包
./package-offline.sh --artifact code --output /绝对路径/交付目录

# 检查镜像和模型是否齐全，不导出大镜像文件
./package-offline.sh --artifact images --verify-only --output /绝对路径/检查目录
```

模型和frp二进制位于其他目录时，分别使用`--model-dir`、`--frp-bin-dir`。打包不会覆盖同名旧归档，不清理已有交付目录。当前无Git提交时，版本记录真实的文件树摘要及不可用的HEAD，不伪造提交号。

## 目标服务器

目标需要Docker、Compose v2、Python 3.11或更新版本、tar、sha256sum，以及足够的磁盘和内存；业务运行无需安装Node、pnpm、编译工具或模型SDK。镜像包的架构必须匹配目标。公网入口另需配置可访问地址、网关及TLS证书。

先校验归档旁的`.sha256`文件，再解压镜像包。运行其中的`load_images.sh`，用`--deploy-root /绝对部署目录`将已验BGE模型放到该部署的共享目录。已有匹配镜像和模型时可跳过镜像包加载，禁止用删除其他项目镜像来释放空间。

解压代码包，先检查，再明确安装：

```bash
python3 deploy/release/install.py --package /路径/EngramProject_code_版本.tar.gz --deploy-root /srv/engramproject
python3 deploy/release/install.py --apply --package /路径/EngramProject_code_版本.tar.gz --deploy-root /srv/engramproject
```

默认入口仅绑定本机。需要其他电脑访问时，在部署配置中设置实际入口地址、绑定地址和访问源，配置TLS或上层网关后进行验证。不要把模型、数据库、对象存储及内部通道端口直接开放公网。

## 目录与日常操作

```text
部署目录/
├── start.sh / stop.sh        # 部署根的一键启停入口
├── current -> releases/当前版本/
├── previous -> releases/前一版本/
├── releases/                 # 独立业务版本，保留旧版供核对
└── shared/
    ├── .env                 # 本机生成的私密配置，升级保留
    ├── deployment.json      # 部署身份、启用模块和运行参数
    ├── models/              # 低频更新的已验BGE权重
    ├── logs/                # 运维导出的服务日志和升级前归档
    └── backups/             # 升级前数据库备份
```

数据库、对象存储、附件及队列使用固定部署身份的数据卷，不随业务版本目录变化。安装器不得接管另一个部署的容器或卷；普通启停不删除卷。

```bash
cd /srv/engramproject
./start.sh
./stop.sh
python3 current/deploy/release/launcher.py status --deploy-root /srv/engramproject
python3 current/deploy/release/launcher.py logs --deploy-root /srv/engramproject
```

部署根的启停脚本始终选择current，升级后仍使用相同入口，不覆盖自行创建的同名脚本。启动只使用本地已校验镜像，不编译、不拉取。问答模型由管理员在页面配置；内置语义检索由平台接通，无需在每个项目重复填写。OCR保留人工核对要求，不以识别完成表示内容准确。

## 升级、日志与失败恢复

日常升级沿用同一部署根目录，只安装新代码包。运行依赖改变时，先加载新镜像包。升级前应导出旧容器日志并备份数据库，验证迁移和服务健康后再切换`current`；新版本失败时保留旧版本、备份和失败阶段记录。

API、普通后台任务、定时任务、诊断worker、协作、网页访问、向量、OCR及基础服务的标准输出与错误由各容器记录，默认按20MiB×5份轮转。保留量有限，长期归档应导出到`shared/logs/`或接入外部日志存储。业务操作和诊断报告的历史另保存在业务数据库，不等于容器日志。

日志不保存密码、令牌、Cookie和认证头；请求及异常仍保留用于定位的路径、状态和耗时。网页访问日志与浏览器控制台错误不同，当前不把用户浏览器中的全部控制台内容自动上传服务器。

检查服务可使用`launcher.py status`，日志可使用`launcher.py logs`导出。若存在未完成部署事务，先核对记录、迁移与备份，不直接删除事务标记或强行切版本。数据库迁移不能仅通过切回旧代码目录撤销；涉及不可逆迁移须制定恢复方案。

## frp按需启用

frp源码位于`deploy/network/frp-bridge/`；交付产物位于统一交付目录的`optional/frp/`，独立解压和配置。公网端及指定的联网采集网关各运行对应角色，数据平台无需安装frp；普通内网直接连接。首次配置和验证完成后，采集员继续按原DAQ流程操作。

frp包只提供检查及显式启动入口，不自动安装系统服务或修改网卡、路由、防火墙和DNS。密钥与证书由部署人员在目标环境配置，不写进交付包。详细配置见frp包内README。

## 验收范围

157历史知识包首次仅暂存；管理员初始化并明确目标私有项目后，使用seed_knowledge.py显式导入待复核草稿。导入成功记录全库初始化标记，以后升级不再读取新种子，更不会覆盖后续知识；草稿未发布不能称已进入检索。

首次部署应验证登录、项目权限、附件上传下载、后台队列、诊断及知识检索；升级应验证数据、附件、配置和日志保留以及运行镜像ID未无故变化。当前开发过程的测试报告与目标环境验收分别记录，不能由打包成功推断部署成功。

## 五种业务角色

| 角色 | 职责 |
| --- | --- |
| 管理员 | 全部岗位业务及平台设置，可自行提交、处理、审核、确认和关闭，操作记录使用本人身份 |
| 项目经理 | 项目成员岗位、需求与任务、缺陷分派、方案审核、测试最终确认、项目发布和报表 |
| 技术员 | 分析分派问题、提交技术方案和修复结果、发起验证、补充经验知识 |
| 测试员 | 维护用例、套件、测试计划和资源，安排执行、提交结果，发起回归和生成测试报告 |
| 数采员 | 采集任务、上报问题、补充本人材料、查看获授权的处理结果 |

技术员和测试员是预置岗位。管理员可新建本地账号并分配项目岗位，也可为已有数据平台账号调整岗位，无需重复建号。数据平台账号仍由原平台维护密码；项目岗位调整不回写来源角色。

来源首次对应固定为Admin→管理员、Manager→项目经理，TeamLeader／Annotator／Auditor／Collector→数采员。之后管理员在本平台调整的岗位会保留，重复登录不恢复默认岗位；来源停用和项目撤权仍继续核验。页面统一称管理员，后台兼容已有权限记录，不要求分别授权多种管理员身份。

测试员不自动获得项目最终验收、发布或全平台设置权限；普通岗位保留原审批边界，管理员无需第二人即可审核本人事项。飞书相关后续完善已延期，不作为本次交付前置。

## 常用入口

统一从“右上角头像 → 设置 → 成员与权限”管理人员。选择项目后，在同一人员表添加成员、修改岗位或兼任；管理员可切换“全部人员”，在同一个编辑入口管理管理员身份。访问范围和业务岗位分别保存，并明确显示保存结果。来源关联、平台连接和模型配置位于同一设置导航，来源关联保留项目选择。管理员拥有全部岗位能力，以本人账号操作和留痕。

项目内“需求”处理正式需求、审批及变更，“任务”及项目保存的任务视图只展示研发任务；跨项目的“工作总览”保留需求和任务综合查询。编号、关联和历史记录保持。测试区保留用例、用例集、计划、执行记录、测试资源和测试结果；发布验收位于“版本迭代 → 发布验收”。文档知识区使用“项目文档、知识库、知识问答、知识管理”等名称。

旧测试配置和模型连接地址会跳转到新入口，并保留项目、查询及页内定位。菜单归位不重建账号、项目或业务记录；已存链接、编号与后端接口继续兼容。
