# 项目平台架构与语言调整设计

状态：初步设计，尚未实施语言迁移或新的性能改动。2026-11-20。

工作分支：`feat/platform-architecture-performance-20261120`。基于 `feat/coverage-followups-152` 的 `8660196d8e198867206bfdb22613addb539bf026` 创建，使用独立 worktree；原功能分支和运行平台不变。

## 结论

保留 TypeScript 前端和 Python Agent。业务后端先治理查询、实时传输和任务隔离，Java 作为局部后端服务的候选方案，通过同负载对比决定是否引入。语言比例不能证明瓶颈，增加 Java 也不会自动解决数据库等待、模型响应或公网链路延迟。

目前不支持全面重写的决定：已有优化记录显示，保留 Python 也能显著减少查询和延迟；尚无本平台 Java 实现的等价压测。稳定性还取决于超时、资源上限、事务、恢复和权限边界，不能由静态类型或某一种语言替代。

## 当前结构与证据

| 层次 | 当前实现 | 调整方向 |
|---|---|---|
| 页面与交互 | TypeScript、React、React Router；共享 UI 和状态包 | 保留，优化资源加载、数据请求和渲染；不用 Java 替代前端 |
| 业务 API | Python、Django 5.2、DRF、PostgreSQL | 先减少重复查询和序列化开销，明确事务和模块边界 |
| 实时终端 | Django ASGI、Channels、Redis 快速缓存、数据库可靠回退 | 单独测量线程等待、查询、事件分发及双端网络时间 |
| 普通后台任务 | Celery 普通队列 | 保持与诊断、现场修复的资源隔离 |
| 诊断与现场处理 | 专用 Celery 队列、Python Agent/模型及执行端 | 保留 Python 生态；约束并发、取消、超时和同机写入 |
| 协同编辑 | 独立 TypeScript/Node.js 服务、Hocuspocus/Yjs | 保留成熟协议与现有服务，不为统一语言重写 |
| Java 相关代码 | 仓库含跨平台桥接验收程序，导入外部数据平台的 Java 组件 | 这是测试集成能力，不能据此认定项目平台已有 Java 业务后端 |

## 优先优化项

以下是需要测量和验证的候选项，不表示已确认故障或已完成改造。

| 顺序 | 候选项与依据 | 首先补充的证据 | 验收要点 |
|---|---|---|---|
| 1 | 实时通道仍定期检查输出/命令，且通过 `database_sync_to_async` 调用同步 ORM | 活跃连接增加时的查询/秒、线程等待、Redis/数据库耗时和端到端 P95 | 事件通知或请求合并必须保留序号、权限撤销、断线回退和真实输出 |
| 2 | 列表、统计、详情可能存在不同的数据加载口径 | 逐入口网络瀑布、SQL 数量、执行计划、载荷、渲染耗时 | 摘要与详情按需加载；分页下权限、计数、筛选和排序一致 |
| 3 | 现有独立队列需持续保证资源隔离 | 普通 API + 模型诊断 + 现场修复 + 终端 + 文件混合负载 | 长诊断不饿死交互；任务超时、取消和执行端重连可恢复；同机互斥保留 |
| 4 | API 启动包含全局 `clear_cache` 及多项初始化 | 核对缓存后端范围、会话用途、并发启动和滚动重启影响 | 先证明必要性，再设计定向失效；禁止未经验证直接移除初始化或清空共享状态 |
| 5 | 通用部署与 5090 运行参数有差异 | 新部署、升级、重启后的实际 worker 数、DB 连接和资源上限 | 参数可配置且有合理默认；300GB/112核是整个平台的资源上限，不是每个服务预留 |

不得通过放宽权限、减少验证、吞掉错误、降低采样量或只比较冷/热缓存获得指标改善。

## Java 的适用边界

| 候选模块 | 是否优先引入 | 条件与代价 |
|---|---|---|
| 账户、权限、项目、缺陷等核心事务 | 暂不迁移 | 与 Django ORM、权限、历史记录和事件紧密关联；重写风险大，当前没有语言瓶颈证据 |
| 高频实时转发或连接服务 | 可做独立验证 | 仅当证实调度、线程等待或 CPU 开销占主要时间；比较现有 ASGI 方案和 Java，而非假定后者更快 |
| 规则计算、统计汇总等独立后台任务 | 可做独立验证 | 先证明 CPU 热点，稳定消息合同和幂等边界，再比较优化后的 Python 与 Java |
| Agent、模型工具和知识处理 | 保留 Python | 模型等待时间不会因换 Java 缩短；重点在上下文、工具边界、并发和失败恢复 |
| 已有数据平台 Java 集成 | 优先复用已有能力 | 核对接口和权限；避免项目平台再建一套账户、令牌与权限事实来源 |

若验证 Java，使用团队维护的 LTS JDK 与兼容的成熟框架。暂不新增 JDK、Spring 服务、消息系统或运行镜像；具体版本以试验时的兼容性和支持周期核对为准。

### 引入条件

1. 从当前分支建立可重复基线，定位到可迁移模块的 CPU、调度或维护问题；网络、模型和数据库耗时分别计量。
2. 优先对现有实现做最小修复，避免拿未优化的 Python 与优化后的 Java 比较。
3. 两种实现采用相同 CPU/内存、数据量、连接数、协议、权限、可靠性和持续时间；同时记录 P50/P95/P99、错误率、吞吐、CPU、RSS/堆及 GC、连接池、排队时间和恢复时间。
4. 收益超过多轮测试波动，且足以承担新增服务、维护、部署和升级成本；具体门槛在拿到基线后冻结，不事后为通过调整。
5. 权限、顺序、数据一致性、故障恢复和实际功能均通过，才能进入灰度。未满足则保留现有实现，并记录试验结果。

### 迁移方式

只从一个清晰模块开始，保持现有 API/消息合同。初期单一写入方，数据库表和事务仍由既有服务负责，不让两套 ORM 直接并发管理同一业务。跨进程增加的网络、序列化和故障点也计入结果。

先以脱敏固定输入和隔离环境对照，再进行只读影子验证，最后按明确路由灰度；不能镜像执行真实修复命令或机器人动作。模型只提出受控计划，原执行端校验与同机互斥保持唯一。回滚通过路由和兼容合同完成，不以还原旧数据库覆盖新数据。

## 实施与交付顺序

1. **本次：** 完成架构初步核查、独立分支和此设计；不修改运行行为或部署。
2. **测量：** 建立页面、API、实时传输、任务队列的分段基线，优先复用现有测试及混合负载工具。
3. **最小改动：** 每次针对一个有证据的瓶颈，补回归并做同条件配对测试；无可测收益的改动不保留。
4. **Java 决策：** 只有达到上述条件，才实施一个模块的对照原型并形成采用/不采用结论。
5. **发布：** 软件回归、混合并发、失败恢复和部署检查通过后，提供变更、指标及回滚说明，再安排上线。
