# 配置修复计划、确认与复查

## 实际闭环

DAQ 上报缺陷及设备身份 → 读取本机有效配置和日志 → 形成恢复候选 → 页面“查看修复计划” → 有权限的人员确认修改值适用于当前机器人 → 单次修复队列 → 执行前重查 → 最小修改及备份 → 读回复查 → 原缺陷和 DAQ 公开回复。

本轮接通配置计划批准的下发，不再要求用户手工放置批准文件。模型不能创建批准，页面也不能任意提交字段或恢复值。当前实现只针对执行端已经具备的 `restore_invalid_initial_joint_states` 适配器；类型、维度、关节组及具体值通用，不写死 TD-D-499/502 的字段或答案。其他文件、依赖、服务及连接类问题需要各自受控适配器，不承诺任意报错可自动修复。

## 页面与状态

缺陷“Agent 现场处理”显示默认收起的计划，包含电脑、文件及实际字段修改前后。默认不勾选批准，展开并确认后才发送请求；重复点击或网络重试复用同一任务，不重复写入。

- 待确认：已有候选，尚未授权。
- 需更新：旧 DAQ 不具备单次计划协议，不能只在平台假装批准成功。
- 已失效：观察过期，或设备/配置变化；需重新诊断并审阅。
- 排队中、排查中、修复中、复测中：沿用同一任务进度及实际命令回执。
- 待验证：配置已修改并复查通过，或者仅配置检查通过；完整状态区分两者，不能写成原故障业务已恢复。
- 未解决/已中断：保留真实阻断、错误或未知执行状态。

确认值来自用户或设备认可证据时如实记录来源。发布包带有正确哈希并不等于已经证明设备标定值正确；仅发布候选仍需要确认，既有独立认可的设备执行策略保留原校验流程。

## API 与执行边界

`GET /api/quality-auth/remote-diagnostics/configuration-plans/?defect_id=<id>` 从该反馈最新固定 inspect/verify 的真实回执形成计划；返回可读目标、changes、观察时间、15分钟有效期及是否可确认。不可从其他电脑、旧任务或模型自由文本生成执行授权。

`POST` 同一路径只接受 `source_run_id`、`plan_digest`、`confirmation=confirmed`。不接收自选路径、命令或恢复值。平台实时校验当前权限、原反馈绑定、设备在线、系统/机器人身份、观察新鲜度、新版本能力及未关闭状态。在设备/源任务锁内记录唯一确认任务；重试返回原任务。

确认后走现有现场队列和同机互斥，固定执行 inspect → repair → verify，不再让模型重新选择或扩大已经确认的操作。inspect 的当前快照、目标、基线和候选值需与批准完全匹配；执行端再次验证相同约束、时效和对应故障证据。单次批准只在固定设备状态目录内受锁保护地安装，修复后清除或恢复原批准；不增加任意 shell、文件写入或运动入口。

旧版本没有 `approval_protocol=robot-config-repair-approval-v1`，页面明确提示更新。新 DAQ 仍按 launch_web → 地址 → 登录使用，升级不得复制别台电脑的身份或批准记录。不同采集员使用同一电脑不新建设备卡片；批准本身只适用于本次快照，不能永久沿用。

## 499/502 与验证口径

499 是 test2 上的 `3.3065` 注错，曾有独立计划写回；502 是 025 上的 `5.3065` 注错，现场正确值由用户确认为 `0.3065`。两例验证的是受控配置恢复，而不是所有业务报错同因。本次没有在 025 安装新包或执行批准/修改，也不把其状态写成已修复。

验证分别保留：

1. 后端 API/授权/幂等/队列回归。
2. 平台确认 → 真正连接器 → 本地 HTTP → 配置适配器的实际隔离文件写入、复查及公开回复。
3. Ubuntu22 对正式部署包中的加固模块实际写入、校验和单次批准清理；不以源码通过替代包通过。
4. 真实模型严格盲测：不在提示或 inspect 中暴露错误键、正确值和隐藏评分目标，模型读取原始配置、独立基线及源码后提交补丁；缺批准的负例不得写入。覆盖越限、类型和维度。
5. 浏览器确认交互、默认折叠、内部编号隐藏、375/768/1440宽度及无自动批准。

盲测历史中一次维度案例改对并通过语义复查，但报告未写技术配置键，严格定位项失败；该原报告保留。增加通用的“root_cause 写出已观察配置键”要求后，新维度正/负例通过，没有调整评分器或向模型提供答案。这证明测试能发现缺口，不代表对几百个源码文件或所有实际故障已全面覆盖。

配置复查不等于复位、运动或采集验收。机器人动作仍由现场明确授权并按原失败操作单独验证，缺陷由负责人决定继续处理或关闭。
