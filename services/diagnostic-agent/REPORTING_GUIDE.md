# 诊断与现场处理报告规范

目标：操作人员先看懂状态和下一步，开发人员可以展开证据定位与复现。整理不改变事实，不扩大验证范围，不生成无依据的代码路径、函数或服务名。

## 默认摘要

按下列顺序输出，不重复标题、编号、时间、版本清单和原始材料内容：

1. 结论：当前故障是否存在，已修复、验证通过或未解决。摘要最多120个中文字符。
2. 原因：一句已确认根因；未确认时明确最关键的缺口。不要把候选原因写成结论。
3. 处理：真正做过的修改；没有修改就说明本轮仅检查。最多4条。
   每项修复明确目标主机/容器、文件完整路径、实际行号与配置键/函数、前后值。缺文件给目标目录与模板来源，缺依赖给解释器/环境、包名版本、安装命令及校验。位置属于必要内容，不能为了缩短而隐藏；行号以实际读取版本为准。
4. 验证：围绕原故障的实际检查结果；不能用模型意见、依赖导入或标准ROS topic替代业务回归。
5. 后续：恢复后只说明是否还需处理；未恢复时给最多4项能执行的步骤及成功条件。

示例：177遥测开关关闭，导致采集返回HTTP503。已开启遥测，195自动复测通过，控制回执、遥测和采集文件正常。无需重启。本次为隔离模拟验证。

重新验证示例：195与177的模拟采集链路正常，未复现HTTP503。本轮未修改配置。

## 开发详情

完整执行记录单独展开，包含可用的版本、时间、文件或函数、配置项、命令结果、修复前后差异、回退文件和复测证据。仅填写本轮真实获取的信息：

- 代码问题：仓库/版本、实际读取的文件与函数、修改点、是否需要构建部署。
- 配置问题：路径、配置项、前后值、校验冲突处理与备份。
- 系统问题：服务或进程名、日志证据、恢复动作；解释为何需重启服务或整机。
- 硬件问题：只确认远程证据能够支持的范围；明确待现场检查内容及验证方法。
- 验证问题：测试入口、退出码、原始错误、关联回执/消息/文件、适用范围。

哈希、长路径、原始字段、各专业组件输出和处理轮次保存在开发详情，不反复复制到默认摘要。不同轮次均保留；历史成功不等于当前成功。

## 文风与事实约束

用具体对象和动词，不写空泛套话、开场总结、重复免责声明或“建议联系相关人员”。“检查配置”应说明检查哪个配置和哪项；“已恢复”必须有原故障对应复测。知识库和历史案例是参考；外部材料不能直接授权现场命令。

报告整理由主Agent生成及结构化规则展示，不另起一个有现场权限的改写Agent。模型密钥、口令、token、无关私人文件不得进入报告。彩色标签与明确文字共同表达状态。

## 从连接开始的诊断检查顺序

先识别当前操作电脑与机器人是否已连接：没有成功连接、连接失败、已连接业务未就绪、运行后掉线分别处理。不得从草稿地址或历史日志推断当前连接成功。检查应覆盖物理网口/无线状态、路由/IP、基础可达、SSH身份、机器人服务，再进入ROS/DDS/Topic、遥操控制回执与采集业务。

每个诊断项和修复项、验证项使用同一编号和对象。缺依赖定位到准确Python解释器/虚拟环境/容器；缺配置定位到完整路径及模板；配置错误给实际文件行号、键与前后值；代码调用错误给实际读取版本的文件与函数和调用边界；网络问题给目标、端口与失败阶段。失败或未定位先补证，不把安装包、重启服务或改配置当通用动作。
