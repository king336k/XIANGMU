# Remote diagnostic framework boundaries

The central `services/diagnostic-agent/remote_runner.py` accepts one JSON stdin object with `config: {model, api_key, base_url}`, `gateway_url`, `tool_token`, `problem`, and `context`. It emits one JSON report. Credential values and provider exception text are not logged. Device authorization remains enforced by the gateway; model-supplied purpose labels are evidence bookkeeping, not an authorization boundary.

The runner independently classifies exact trusted `inspect_argv`/`verify_argv` and configured specialist commands as reads; any other run command is a mutation regardless of its model-supplied purpose. A read-only task rejects it. Failed/timed-out latest verification clears a previous pass. The gateway must enforce the same classification independently.

`requirements-central.txt` extends the existing PydanticAI 2.66.0 environment with LangGraph 1.2.22. With LangGraph installed, actual execution follows `START → diagnose (PydanticAI tools) → verify_evidence → END`. It does not currently persist/resume graph checkpoints. Without LangGraph the typed agent still operates, and the local probe reports the missing integration honestly.

Tool RPC POST uses the scoped Bearer token. Operations: `run` with `argv/cwd/timeout`; `read_file` with `path`; `patch_file` with `path/expected_sha256/content`. The server returns an object: run uses `exit_code/stdout/stderr`; read uses `content/sha256`; errors use `error`. No redirects or environment proxies are followed. The gateway must independently enforce target scope, command allowlists and write authorization. The runner cannot make arbitrary shell commands safe.

Specialist bridges expose only fixed read-only operations: `specialist.py rosa health|inspect`, `rai health|inspect`, `holmes health|inspect`. ROSA invokes its real ROS2 node/topic/service tools; RAI invokes its real 1.1.0 `Ros2GetTopicsNamesAndTypesTool`. Neither exposes motion, topic publication, parameter writes or arbitrary command arguments. Holmes can consume the fixed SRE bridge through `holmes-toolsets.yaml`; launch local investigations with `holmes ask ... --custom-toolsets=/opt/diagnostic-integrations/holmes-toolsets.yaml` and your separately managed provider config. The snapshot itself is a data source, not evidence that a Holmes model investigation ran. The central coordinator instead uses the separate credential-isolated `holmes_runner.py` described below.

For gateway allowlists, approve the exact interpreter + absolute specialist.py + role + operation prefix. `context.specialists` may declare these exact argv lists; only populate this context from trusted server configuration, never from uploaded task text. Device bridge scripts can be deployed inside an existing robot container; absence of host ROS does not establish container absence. Robot-container transport and its fixed gateway prefix must be explicitly configured.

`context.required_specialists=["rosa","holmes","rai"]` requires the coordinator to call all three specialist integrations before accepting a final report; this records unavailability honestly rather than pretending missing frameworks ran. Configure this after the primary gateway repair path is validated. `inspect_argv` and `verify_argv` are enforced as exact trusted command arrays; `repair_allowed=false` rejects repair tools.

Never install PyPI `rai`: it is an unrelated radiotherapy.ai package. The install helper uses official RobotecAI Git source at tag 1.1.0, its committed Poetry lock and colcon build in a dedicated environment. ROS/system dependencies are prerequisites; this helper does not alter the host ROS installation or existing robot containers. Upstream 1.1.0 has substantial voice/vision dependencies; installation is not claimed tested on the robot. Current upstream main 7b75a3d requires Python3.12/Jazzy, so do not silently update the pin. Cross-distro ROS communication is not assumed.

ROSA plus the central LangGraph loop covers read-only ROS topology/parameter diagnosis and tool-driven repair coordination on Humble if RAI installation is blocked. This does not replace RAI voice/vision, robot identity, action planning or navigation capabilities. This integration intentionally exposes only read-only RAI topic discovery; model-driven motion/navigation is outside the diagnostic bridge.
